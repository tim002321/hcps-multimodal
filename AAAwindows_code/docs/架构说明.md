# AAAwindows_code 程序逻辑说明

> 面向接手阅读的人：先看这一篇，能回答「数据从哪来、经过谁、落到哪」三个问题。
> 代码位置见各节标注；目录结构见文末「目录速查」。

---

## 1. 这个程序是什么

Windows 上位机上的**多设备生理数据采集程序**：

- 通过蓝牙（BLE，`bleak`）接收 **心电贴** 和 **绿光手环** 的数据；
- 通过 USB 摄像头按 30fps 采集画面（OpenCV）；
- 三路数据写进**同一个 SQLite 会话库**，时间轴天然对齐；
- 提供两种运行形态：`main.py` 纯采集、`run_monitor.py` 采集 + 实时监测界面。

数据规模参考（实测）：

| 通道 | 采样率 | 说明 |
|---|---|---|
| 心电 ECG | 250 Hz | 每包 80 点，约 3.125 包/秒 |
| 呼吸 | 25 Hz | 每包 8 点 |
| 心电贴三轴 | 50 Hz | 每包 16 点 |
| 体温 | 随包 | int16 / 100 |
| 手环 PPG | 250 Hz | 4 通道 × 10 点/包，25 包/秒（40ms 一帧） |
| 手环 GSR | 10 Hz | 1 秒一包，10 个样本 |
| 手环肤温 | 0.1 Hz | 10 秒一次 |
| 摄像头 | 30 fps | 640×480 / JPEG80 ≈ 25~40KB/帧 |

```
                  （纯采集入口）              （采集 + 界面入口）
                        │                          │
                        └──────────┬───────────────┘
                                   │  都只用下面这层
                    ┌──────────────▼──────────────┐
                    │        devices/（设备层）     │
                    │  ecg_receiver     心电 BLE   │
                    │  bracelet_receiver 手环 BLE  │
                    │  bracelet_protocol 手环协议   │
                    │  camera_receiver   摄像头     │
                    │  ble_utils         BLE 公共   │
                    └──────────────┬──────────────┘
                                   │  只依赖 core，不依赖 ui
                    ┌──────────────▼──────────────┐
                    │         core/（核心层）       │
                    │  config        ini → Config  │
                    │  db_storage    SQLite 存储    │
                    │  writer_thread 写库线程       │
                    │  device_status 设备状态表     │
                    └──────────────────────────────┘

                    ┌──────────────────────────────┐
                    │          ui/（界面层）        │
                    │  base      页面基类/曲线网格   │
                    │  buffers   实时缓冲 + 入库钩子 │
                    │  replay    历史库/JSONL 回放   │
                    │  window    主窗口 + 两级导航   │
                    │            采集六页在位内      │
                    │  pages_extra 会话/识别/分析    │
                    │  profile   登录与被试信息      │
                    │  widgets / theme   组件与配色  │
                    └──────────────────────────────┘
```

**依赖方向是单向的**：`ui → devices → core`。设备层完全不认识界面，
这也是同一套接收代码既能在 `main.py` 里裸跑、又能在 `run_monitor.py` 里带界面的原因。

唯一的「反向」连接靠**继承**实现，不是靠 import：

```python
# ui/buffers.py
class MonitorRecorder(DataRecorder):        # 继承 core 的入库器
    def record(self, decoded, ts=None):
        super().record(decoded, ts)          # 照常入库
        self.buffers.publish_ecg(decoded, ts)  # 顺手推给界面缓冲
```

`run_monitor.py` 把 `MonitorRecorder` 交给设备层，设备层只当它是 `DataRecorder`。

## 3. 一条数据从设备到数据库到界面

以心电为例（手环同构，只是协议不同）：

```
① BLE 通知到达（asyncio 事件循环线程）
      on_notify(sender, data)
      ├─ payload = bytes(data)                    只做字节拷贝
      └─ writer.submit(lambda: process(payload, received_at))   入队，立即返回

② 写库线程 SensorWriter（单线程串行）
      process(payload, received_at)
      ├─ PacketAssembler.feed()      分片重组 → 完整 244 字节包
      ├─ decode_ecg_packet()         struct 解出 ECG/呼吸/三轴/体温
      ├─ output.emit()               可选写 JSONL
      └─ recorder.record(decoded, ts=received_at)
            ├─ storage.insert_many("ecg_data", ...)     入 SQLite（批量提交）
            └─ [界面形态] buffers.publish_ecg(...)      推给界面缓冲

③ 界面（Qt 主线程，QTimer）
      _on_data()  每 40ms   取 buffers 快照 → 各页重绘曲线
      _on_tick()  每 1000ms 算速率 / 刷状态栏 / 同步摄像头状态
```

### 3.1 为什么一定要有写库线程

这不是「为了好看」。`core/writer_thread.py` 的注释里记着实测数据：

> 把 SQLite 写入 / JSONL 落盘 / 打印直接放在 BLE 通知回调（事件循环线程）里执行，
> 手环 PPG 会从标称 25 包/秒掉到 13~15 包/秒，**按同一比例整条丢帧**；
> 单设备不写库时稳定 25 包/秒、计数戳逐包 +1、零丢失。

所以铁律是：**通知回调里只做字节拷贝和入队**。
`SensorWriter` 队列上限 20000，满了丢最旧任务并计数（`stats['dropped']`），
宁可丢老数据也不让内存无限涨。

### 3.2 为什么时间戳要在回调里取

`received_at` 在通知回调里生成，而不是在写库线程里生成：

> 否则队列有积压时，心电时间轴会相对摄像头整体后移。

摄像头侧同理，`captured_at` 在 `cap.read()` 之后、JPEG 编码之前取。
两边的「事件发生时刻」都用同一个系统时钟，回放时才能对齐。

## 4. 三路设备的接入细节

### 4.1 心电贴（`devices/ecg_receiver.py`）

- **发现**：按广播名匹配（`config.ini` 的 `device_names`，支持多个）。
- **握手**：写 handle 20 / 25 为 `0x0100`（bluepy 时代手动使能 CCCD，bleak 下可省略）；
  再用 handle 22 依次下发「结束采集」「开始采集」两帧。
- **订阅**：服务 `554b0001-15e1-4af1-a6e3-588089f20b68` 的第一个特征，找不到则退回任意 notify 特征。
- **组包**：244 字节一包。Windows 蓝牙栈 MTU 不够时设备会拆成多条通知，
  由 `PacketAssembler` 按包头 `0x5B` / 包尾 `0x5D` 对齐重组，并对齐失败时向后找下一个包头。
- **解码**：`decode_ecg_packet()` 用 `struct.unpack_from` 直接读原始字节（改造前是 `hexlify` 成 ASCII 再解析）。
- **断线**：`while True` 外层循环，异常/掉线后 sleep 3 秒重连。

### 4.2 绿光手环（`devices/bracelet_protocol.py` + `bracelet_receiver.py`）

协议与蓝牙**彻底分开**：

- `bracelet_protocol.py` 是纯函数层：喂字节、出 `PPGAccelData` / `GSRData` / `SkinTempData` / `BatteryData`。
  没有任何 `bleak` 依赖，可以离线用协议文档里的示例帧验证（见 `legacy_bracelet.py --demo`）。
- `bracelet_receiver.py` 只负责扫描、连接、订阅、把字节喂给解析器。

两类帧的差别：PPG 帧比其他三类多 2 字节计数戳，所以载荷偏移是 11 而不是 9；
PPG 载荷 166 字节 = 160 字节 PPG（4 通道 × 10 点 × 4 字节，其中 1 字节状态 + 3 字节 24bit 数据）
+ 6 字节腕部三轴。

**24bit 有符号处理**是这里最容易错的地方：文档公式 `(b0<<24|b1<<16|b2<<8)/256`
等价于把 3 个字节按 24 位有符号整数解析（`raw24 & 0x800000` 时减 `0x1000000`）。
手环 PPG 原始值是几十万到几百万量级的直流偏置，界面上必须先做交流耦合（`ac_couple`）才能看出脉搏波。

**通知特征**：`notify_uuid` 指定 → 常见透传 UUID 列表 → 任意 notify/indicate 特征，
三级回退，所以换个手环型号通常不用改代码。

### 4.3 摄像头（`devices/camera_receiver.py`）

两个线程：`CameraCapture`（读帧 + 编码 + 入队）和 `CameraWriter`（批量入库）。

要点：

- **固定节拍**：`next_due += interval` 推进，而不是「从现在起再等 33ms」。
  否则 JPEG 编码耗时会被算进周期，实测 60fps 源只能出 20fps。
- **超帧丢弃**：摄像头比目标帧率快时，早于 `next_due` 的帧直接丢掉并计数。
- **二次缩放**：有些 USB 驱动忽略 `CAP_PROP_FRAME_WIDTH/HEIGHT`（1080p 驱动不认 640×480），
  所以拿到帧后再 `cv2.resize` 一次，保证入库体积可控。
- **入库**：JPEG 原始字节直接进 BLOB，分析端 `cv2.imdecode` 即可用。

## 5. 存储模型（`core/db_storage.py`）

一个会话 = 一个库文件 `data/YYYYmmdd_HHMMSS.db`（同秒重复启动会追加 `_01`）。
库里**一个信号一张表**，所有表统一两列：

```sql
CREATE TABLE {表名} (time TEXT, value TEXT)   -- value 是 JSON
```

| 表 | 内容 |
|---|---|
| `ecg_data` | 每个采样点一行（80 行/包） |
| `breath_data` / `triaxial_data` | 同上 |
| `temperature_data` | 每包一行（标量） |
| `bracelet_ppg_data` | 每个采样点一行 `{"PPG1":..,"PPG2":..,"PPG3":..,"PPG4":..}` |
| `bracelet_accel_data` | 每包一行 `{"x":..,"y":..,"z":..}` |
| `bracelet_gsr_data` / `bracelet_skin_temp` / `bracelet_battery` | 按上报频率 |
| `camera_frames` | 每帧一行，`jpeg` 是 BLOB |

三个性能设置（都是踩坑后加的）：

```python
PRAGMA journal_mode=WAL;      # 摄像头帧与传感器同库并发写
PRAGMA synchronous=NORMAL;    # WAL 下够安全，fsync 次数大减
PRAGMA busy_timeout=5000;     # 两个连接写同一个文件时避免瞬时 locked
```

批量提交：累计 500 行或距上次提交超过 0.5 秒才 `commit()`，避免每条记录一次 fsync。
写库线程每 0.5 秒还会主动 `flush()` 一次，保证低频信号（肤温、电量）也能及时落盘。

**两张不同的表为什么能对齐？** 同一个数据包的所有行共享同一个 `time` 字符串，
回放时按 `time` 分组就能把「一行行采样点」还原成「一个包」（见 6.2）。

## 6. 界面层

### 6.1 实时缓冲与刷新（`ui/buffers.py`）

`LiveBuffers` 是一堆定长 `deque`：心电/呼吸/三轴/PPG 各 12 秒，GSR 60 秒。
它**只有一把锁**，写入方是写库线程，读取方是界面线程：

> 写线程不碰任何 Qt 对象，界面线程不碰 BLE —— 两边只通过这把锁交接数据。
> （跨线程操作 Qt 控件会导致访问违例，另一个项目踩过 0xC0000005。）

刷新节奏：40ms 一次取快照画曲线（约 25 帧/秒），1000ms 一次算速率、刷状态栏。

界面上心率不是硬算的。`estimate_heart_rate()` 前面有一道 `ecg_signal_quality()`，
因为实测发现电极没贴时设备照样按 250Hz 推 ±1 的噪声，硬算会报出 190+ 的假心率 ——
所以信号过弱/饱和时直接显示 `--`。呼吸通道同理（有的设备这一路固定上报 0）。

### 6.2 回放（`ui/replay.py`）

回放把历史库当成实时数据源，用途是「没有硬件也能开发和复盘」。

核心是**反序列化**：按 `time` 把行分组，重新拼回 decoded 字典。
老版本把摄像头单独存在 `camera_*.db`，所以还有个按文件名时间就近配对的兼容逻辑。

`ReplayPlayer` 是个线程，按原始时间节奏（可倍速）把包喂进 `LiveBuffers`，
所以回放时界面代码一行都不用改。

### 6.3 设备状态机（`core/device_status.py`）

```
idle → scanning → connecting → connected
                     ↓            ↓
                   error        lost → （3~5 秒后）connecting
        scanning（连续 N 次未找到）→ not_found →（继续重试）
```

`scan_attempts`（默认 10）的意义：**不会扫一次没找到就报失败**。
第 1~10 次显示「扫描中 第 k/10 次」，连续 10 次都没扫到才显示「未找到」，
但后台仍按间隔重试 —— 设备开机后会自动连上，不需要重启程序。

状态表是 BLE 线程写、界面线程读，所以内部加锁，`snapshot()` 返回副本。

## 7. 线程与进程清单

| 线程 | 归属 | 职责 |
|---|---|---|
| 主线程 | asyncio（main.py）/ Qt（run_monitor.py） | 事件循环 / 界面 |
| `ble-service` | run_monitor.py | 在后台线程跑 asyncio，让 Qt 主线程保持干净 |
| `sensor-writer` | core/writer_thread.py | 串行执行解析/入库/落盘 |
| `camera-capture` | devices/camera_receiver.py | 读帧、编码、入队 |
| `camera-writer` | devices/camera_receiver.py | 批量写 `camera_frames` |
| `replay-player` | ui/replay.py | 回放时按时序喂缓冲 |

注意 `main.py` 没有 `ble-service`：它直接在 `asyncio.run()` 里跑，因为不需要界面线程。

## 8. 启动时序（`run_monitor.py`）

```
1. Config.load()                         读 config.ini
2. SensorDB(...) + MonitorRecorder      建库、建表
3. SensorWriter.start()                 起写库线程
4. create_app() + MonitorWindow.show()   建界面
5. 用户点「开始采集」或 --auto-connect
   ├─ BleService.start()               后台线程起 asyncio → 心电/手环接收协程
   └─ window.start_camera()            起摄像头采集 + 写库线程
6. 关窗口 / 点「结束采集」
   ├─ BleService.stop()                取消 task
   ├─ camera_service.stop()            停采集，排空队列
   └─ writer.stop() → storage.close()   排空队列、提交、关库
```

## 9.2 界面结构与导航

侧边栏两级，一级是工作阶段，二级是具体页面（`ui/window.py::NAV_SECTIONS`）：

| 一级 | 二级 | 类 |
|---|---|---|
| 采集 | 设备准备 / 心电 / 手环 / 摄像头 | `PrepPage` / `EcgPage` / `BraceletPage` / `CameraPage` |
| 采集 | 肌电 / 眼动（预留） | `EmgPage` / `EyePage` |
| 数据查看 | 会话与回放（含删除库） | `StatusPage` |
| 状态识别 | 实时结果（四模型） | `RecognizePage` |
| 数据分析 | 区间分析（时间勾选 + 特征提取） | `AnalysisPage` |

曲线横轴是**会话绝对秒数**（从 0 单调递增），由各页面的 `channel_end_time()` 用计数器换算，
不再是「末点对齐 0」的负计数。

## 10. 想改点什么的时候

| 需求 | 改哪里 |
|---|---|
| 换心电设备/协议 | `devices/ecg_receiver.py` 的常量与 `decode_ecg_packet` |
| 新手环型号 | 先在 `bracelet_receiver.find_notify_char` 里加 UUID，再改 `bracelet_protocol._layout` |
| 加一个新传感器 | `core/db_storage.DataRecorder` 加 `record_xxx`，`devices/` 加一个 `start_xxx` 协程，入口 `tasks` 里加一项 |
| 改表结构 | `core/db_storage.py`（表名常量集中在文件头） |
| 改界面配色/布局 | `ui/theme.py`、`ui/widgets.py`、`ui/window.py` |
| 调采样/帧率/批量大小 | `config.ini` 的 `[storage]`；摄像头参数在界面上或 `CameraService` 的 config |
