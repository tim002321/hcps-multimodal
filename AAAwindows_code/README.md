# 蓝牙生理数据采集程序（Windows 11）

在 Windows 11 上位机上直接接收**心电贴 + 绿光手环 + USB 摄像头**三路数据并统一入库，
不再需要 Linux 盒子转发。

- 心电/手环走 BLE（`bleak`，WinRT 后端，替代原 Linux 版的 `bluepy`）
- 摄像头走 OpenCV，按目标帧率（默认 30fps）截帧、JPEG 入库
- 三路数据写进**同一个会话库**，时间轴天然对齐
- 提供纯采集入口 `main.py` 与实时监测界面 `run_monitor.py`

> 先读 **[docs/架构说明.md](docs/架构说明.md)** 了解数据流与分层；
> 想了解这次目录调整改了什么，看 **[docs/重构说明.md](docs/重构说明.md)**。

## 界面结构：三段式向导

**没有侧边栏**，整个流程分成三段，一段一屏，用底部按钮推进，上一步没完成进不了下一步：

```
① 采集 ─→ ② 回放与选段 ─→ ③ 回放观看 ─→ ④ 数据分析
        ←─[上一步]─        ←─[上一步]─     ←─[上一步]─
```

| 段 | 内容 | 完成条件 |
|---|---|---|
| ① 采集 | 标签页：设备准备 / 心电 / 手环 / 摄像头 / 肌电 / 眼动 / 实时结果 | 点「结束采集」**且**本次确实采到数据 |
| ② 回放与选段 | 人员 → 会话 → 设备在线时间轴 → 拖选区 / 自动选区 | 拖出区间或点「自动选区」，再点「进入回放观看」 |
| ③ 回放观看 | 整屏放画面：左摄像头大图，右按勾选铺折线图；倍速 / 重新播放 / 停止 | 进入即自动播放选中片段，看完点下一步 |
| ④ 数据分析 | 下拉选择分析模型 → 特征提取 → 导出 CSV | 至少跑出一个有效模型结果 |

**为什么选段和观看分两屏**：选段那页控件多（人员/会话/时间轴/勾选），图挤在下面只有巴掌大；
拆开后第③屏整屏给图像，选段页专心做选择。

- 顶部阶段条显示 `✓ 已完成 / ● 当前 / 灰底锁定`，未解锁的点不进去。
- 已完成的段可以「上一步」回去重做；重新开始采集会把后面几段的完成状态收回。
- **采集段的设备标签页只显示启动时勾选的设备**（详见下节）。

启动 `run_monitor.py` 会先弹「本次使用」：选做采集还是直接看历史（回看会跳过①直接进②），
再勾测量工具；采集模式下 **人员姓名 / 任务名 / 时间** 决定会话目录
`data/<人员姓名>/<任务名>_<时间>/` —— **人员姓名是第一级文件夹**，
同一个人的多次任务都归在同一个目录下。

启动 `run_monitor.py` 会先弹全屏的「新建任务」：人员姓名 / 任务名 / 时间决定会话目录
`data/<人员姓名>/<任务名>_<时间>/`。

**部署**一栏选「地面」或「上机」：选上机会提示「请确认 IP 地址和上位机的地址一致，可连接」。
**IP 显示的是本机地址，自动读取、只读不可改**（`ui/profile.py::local_ip()`：用 UDP
查一次默认路由拿出口 IP，不实际发包，所以离线也能拿到网卡地址）。
两栏都只是记录，暂不驱动数据上传。

回放与分析的会话选择是**两级**：先选「人员」（文件夹），再选该人员下的具体任务。
`data/` 根目录下的旧会话归在「未分类」里。

## 环境要求

- Windows 10 / 11（已启用蓝牙并插入蓝牙适配器；摄像头可选）
- Python 3.8+（建议 3.10+）

## 安装

```powershell
cd AAAwindows_code
pip install -r requirements.txt
```

## 运行

```powershell
# 纯采集（只写库，可选写 JSONL）
python main.py

# 带界面实时监测
python run_monitor.py
```

常用参数（两个入口都支持）：

```powershell
# 指定心电设备名（多个用英文逗号分隔）
python main.py --device E1220511000413,E1220511000444

# 只要心电，不连手环
python main.py --bracelet ""

# 扫描 15 秒
python main.py --scan 15

# 连接后打印服务/特征表（排查 handle 时使用）
python main.py --debug

# 不写 JSONL 文件（只入库）
python main.py --out none
```

也可以在 `config.ini` 中配置默认值。

> 控制台只打印「连接成功」「设备掉线」两类日志，采集数据不再打印。


## 工作流程

1. 扫描蓝牙广播，按广播名称匹配目标心电设备；
2. 连接后按原协议下发握手命令：
   - handle `20`、`25` 写 `0x0100`（使能）；
   - handle `22` 依次写“结束采集”、“开始采集”命令；
3. 订阅服务 `554b0001-15e1-4af1-a6e3-588089f20b68` 的第一个特征的通知；
4. 收到 244 字节数据包后解码，输出 JSON，并可选写入 JSONL 文件；
5. 断开后自动重连。

### 设备准备（第一页）

启动后先到「00 设备准备」：点「开始连接」会按顺序做

1. 扫描蓝牙广播（心电贴 + 绿光手环）
2. 连接心电贴（bleak，握手后订阅通知）
3. 连接绿光手环（自动发现通知特征）
4. 打开 USB 摄像头（cv2，默认 640×480 @30fps）
5. 三个设备都 `connected` 后显示绿色「设备已全部连接，可以开始采集了」

三张卡片实时显示设备状态：未开始 / 扫描中 / 连接中 / **已连接** / 已掉线 / 连接失败，
下面一条条列出连接流程的进度；「重新扫描」会断开重连，「全部断开」复位。
连接状态由 `core/device_status.py` 的 `DeviceStatus` 记录（BLE 线程写、界面线程读），
接收模块新增 `status=` 参数上报 `connecting/connected/lost/error`，界面不解析日志。

**扫描策略**：不会扫一次没找到就报失败。心电贴和手环各自连续扫描
`scan_attempts` 次（`config.ini` 默认 10 次，每次 `scan_timeout` 秒）：

- 第 1~10 次：状态显示「扫描中 · 第 k/10 次扫描」；
- 连续 10 次都没扫到：才显示「未找到 · 已连续 10 次扫描未找到，仍在重试…」，
  后台继续按间隔重试，设备开机后会自动连上。

验证这条逻辑（不需要设备）：

```powershell
python tools/ble/ble_retry_test.py
```

启动时想直接连设备：`python run_monitor.py --auto-connect`。

### 一次实验的完整流程

启动会先弹「本次使用」对话框，定两件事：

1. **做什么** —— `开始采集`（建新会话）或 `直接查看历史（回放 / 分析）`（不连设备、不建目录，
   直接跳到「会话与回放」）。
2. **用哪些测量工具** —— 心电贴 / 手环 / 摄像头可勾选；表面肌电、眼动仪是预留项，
   置灰不可选（只有占位页，选了也没有功能）。

勾选结果**真的会改变采集段的标签页**：没勾的设备，对应页面根本不会注册。
页面注册表在 `ui/window.py` 的 `PAGE_SPECS`（key / 标题 / 分区 / 类名 / 依赖设备），
新增页面只改这一处；它归哪一段由 `STAGE_OF_KEY` 决定。

采集结束后的路径是「回放选段 → 分析」，两个页面之间靠窗口上的 `review_selection`
传递 `(库路径, 起, 止)`，不需要在分析页再选一遍会话：

```
会话与回放 → 时间轴拖出区间（或点「自动选区」）→ 进入分析 → 选择模型 → 出结果
```

分析模型是**单选下拉菜单**，一次只跑一个：

| 菜单项 | 状态 | 说明 |
|---|---|---|
| 疲劳状态 | 未接入 | 缺少疲劳模型权重 |
| 异常情绪 | 未接入 | 缺少情绪模型权重 |
| 异常行为 | 未接入 | 缺少行为模型权重 |
| 错觉 | 未接入 | 缺少错觉模型权重 |
| **生理指标分析** | **可用** | 心电 HRV + 脉搏 PPG + 皮电 GSR，纯规则计算，不需要模型文件 |

前四项选中后，结果区会明确写「未接入」并禁用执行按钮 —— 没有权重就不出假结果。
「实时结果」页的四个模型卡片用同一套名字，两处不会各叫一套。

### 生理指标分析（唯一可用的那一项）

| 信号 | 指标 |
|---|---|
| 心电 | 心跳数、bpm、SDNN、RMSSD、pNN50、SD1、SD2、VLF/LF/HF、LF/HF |
| 脉搏 PPG | 脉搏波个数、脉率、脉间期均值/标准差、脉搏幅度 |
| 皮电 GSR | 皮电均值、基线 SCL、动态范围、标准差、斜率、SCR 次数/频率/幅度、相位功率 |

皮电有两处需要注意：

1. **单位是「原始刻度」**，不是 μS。设备没有给标定系数（实测值域 0~2.3、量化阶 0.001），
   强行标成物理单位只会让人误以为准。要换成 μS 得先拿到传感器的换算公式。
2. **很多会话的皮电全程恒定**（实测 9 个库里有 3 个只有 1~2 个不同取值）。这类库会显示
   「皮电几乎恒定」而不是硬算出一堆 0。质量闸门用的是相对量（相对量化阶），
   不是绝对阈值 —— 弱信号是正常的，恒定才是没贴合。

门控也跟着改了：只有真的算出至少一路指标才点亮第 4 段。选「错觉」跑一次不算完成。

**时间轴**把每台设备的在线时段画成一条横条（心电贴蓝 / 手环绿 / 摄像头黄），
上面压一个可拖两端的选区，因此「为什么选出这一段」是看得见的。

**自动选区**按**设备**算交集，不按表：一台设备只要有任意一路有数据就算在线，
它的区间取各表并集，交集 = 各设备「最晚开始 ~ 最早结束」。这样才算「戴上了、连上了」；
按表算的话，手环 PPG / GSR / 电量起止能差几十秒，几乎选不出任何一段。
交集为空时如实提示缺哪台设备，不会给一个 0 长度区间。

三个采集页面：

* **心电**：ECG、三轴 X/Y/Z、体温；心率用峰值法实时估计，**信号过弱/饱和时显示 `--`**。呼吸通道暂不显示也不入库（`SHOW_RESP` / `SAVE_RESP`）
  （实测发现电极没贴时设备仍按 250Hz 推 ±1 的噪声，硬算会报出 190+ 的假心率）。
* **手环**：4 通道 PPG（自动做交流耦合，否则 24bit 原始值的直流分量有上百万）、GSR、腕部三轴。
* **状态**：设备连接状态、包数/采样点统计、回放控制。
  上方是文件选择 / 倍速 / 开始-停止，以及**回放内容**勾选列表（库里实际有数据的表
  才会列出来，空表不列）；中间是**设备在线时间轴**（可拖拽选区）和"第 k/N 包"。
  下方左侧是**摄像头画面单独占一块大版面**（回放库里没有帧时自动配对 `camera_*.db`，
  再没有就切到当前摄像头实时画面）；右侧按勾选动态铺折线图 —— **勾一项出一条，
  取消就收掉**，最多 8 条（心电 / 呼吸 / 三轴 / 体温 / PPG / 腕部三轴 / GSR / 电量）。
  手环肤温暂时不在界面露出（`SHOW_SKIN_TEMP = False`），数据仍照常入库。
  点列表某一行，对应那条图标题前会加 `▶` 并滚动到可见位置；点"摄像头帧"则给画面加蓝框。

## USB 摄像头（30fps 入库）

界面第 3 页「摄像头」：选设备号/分辨率/目标帧率/JPEG 质量 → 「开始采集」，
左边实时预览，右边是设置；顶部显示**已入库帧 / 库大小**。
页面右上角有**「开始采集」/「结束采集」**两个按钮（每个页面都有）：
开始 = 扫描蓝牙 + 打开摄像头，结束 = 断开全部设备（设备在跑时开始键置灰，反之亦然）。

也可以不开界面单独采：

```powershell
python -m devices.camera_receiver --index 0 --seconds 10 --fps 30
python -m devices.camera_receiver --index 0 --width 1280 --height 720 --quality 80
```

**数据库**：摄像头帧和心电/手环数据**写在同一个会话库**（`data/YYYYmmdd_HHMMSS.db`），
只是表不同，回放时一起读，时间轴天然对齐。

```sql
CREATE TABLE camera_frames (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    time TEXT NOT NULL,            -- %Y-%m-%d %H:%M:%S.%f
    camera TEXT,
    frame_index INTEGER NOT NULL,  -- 从 1 递增
    width INTEGER, height INTEGER,
    jpeg BLOB NOT NULL             -- 原始 JPEG 字节，cv2.imdecode 即可
);
CREATE TABLE camera_sessions (
    id, started_at, ended_at, camera, width, height, target_fps, frame_count
);
```

**帧率控制**：摄像头若比目标帧率快（例如 60fps），超出的帧直接跳过；
采样按固定节拍推进，不会把 JPEG 编码耗时算进周期（否则实测只有 20fps）。

**给分析用**：导出入库的帧

```powershell
python tools/camera/export_camera_frames.py data/camera_20261017_143135.db
python tools/camera/export_camera_frames.py data/camera_xxx.db --out frames --every 30   # 每秒取 1 张
```

> 存储估算：640×480 / JPEG80 ≈ 25~40KB/帧 → 30fps ≈ 0.8~1.2MB/s（约 3~4GB/小时）；
> 1280×720 约翻倍。长时间录制建议调低质量或改成「存文件 + 库里存路径」。

验证两类数据确实同库（不需要硬件）：

```powershell
python tools/db/test_shared_db.py
```

没有硬件时用 `--replay` 或第②段的回放面板；截图自检：

```powershell
python tools/ui_screenshot.py     # 用历史数据填满界面，按「阶段 + 标签页」离屏截图到 ui_shots/
```

> 注意：`data/` 里现有的几段录音，心电通道大部分时间是 ±1 的底噪（电极未接触），
> 呼吸通道固定上报 0，PPG 是原始 24bit 值。界面会如实显示并在信号不可用时给出提示，
> 接上电极后重新采一段即可看到真实波形。

**呼吸通道暂不入库**（`core/db_storage.py` 的 `SAVE_RESP = False`）：这一路现场
多数是固定 0，存进去只会在回放里多一条直线。实时曲线不受影响（数据走 `LiveBuffers`），
只是库里没有 `breath_data` 表、回放页也不会列「呼吸」这一项。要恢复改成 `True`。

## 打哈欠检测（疲劳监测）

「摄像头」页可以在实时画面上检测打哈欠，作为疲劳监测的一路指标。
**默认开启**（`config.ini` 的 `[vision] enabled=true`）：进页面时勾选框已勾上，
点「开始采集」后自动加载模型（首次约 2~4 秒，含预热）。不想用就取消勾选。

### 原理与选型

```
摄像头帧 → YOLOv8n-face 检人脸（GPU/CPU）→ 只取画面中间那一个人 → 裁人脸 ROI
        → HippoYD 判张嘴概率（ONNX，经 cv2.dnn，约 2~5ms）
        → 时序状态机（连续张嘴 ≥1.5s 才算一次哈欠，容错 0.3s，冷却 5s）
        → 界面：人脸框 + 疲劳状态 + 哈欠次数
```

### 只识别画面中间的人

现场常常是多人：同事在旁边、有人从镜头后走过。`detect()` 返回的是**按面积降序**的脸，
直接取第一个等于"谁离镜头近就认谁"——旁观者一靠近就会顶掉被试，哈欠记到别人头上。

所以主脸由 `pick_center_face()`（`vision/face_detector.py`）挑，不按面积按位置：

1. 脸中心落在「中线 ± `center_band` × 画面宽」这条带子里的才算候选；
2. 候选里取离中线最近的那个（被试就坐在正前方）；
3. 带子里一个都没有时：画面只有一张脸仍然用它（单人场景，人可能坐得偏），
   有多张脸就返回 `None` —— 宁可这一帧不判定，也不拿旁边的人凑数。

`center_band` 在 `config.ini` 的 `[vision]` 段，默认 `0.25`（中间 50% 宽度）：

| 取值 | 含义 |
|---|---|
| 0.25 | 中间 50% 宽度（推荐，被试坐正前方）|
| 0.40 | 中间 80%（人可能坐得比较偏）|
| 0.5 | 全画面，等于不限制（旧行为）|

标定脚本 `calibrate_threshold.py` 和基准脚本 `bench_yawn.py` 用的是**同一个函数**，
否则会出现"标定时取的脸"和"运行时取的脸"不是同一张，阈值对不上。

两个模型都是现成的，**不需要自己训练**：

| 环节 | 模型 | 大小 | 许可证 |
|---|---|---|---|
| 人脸检测 | [yolov8n-face](https://github.com/akanametov/yolo-face) | 6.4 MB | GPL-3.0 |
| 张嘴判定 | [HippoYD](https://github.com/iglaweb/HippoYD)（YawDD 训练） | 9.8 MB | Apache-2.0 |

### 准备

的 `[vision] backend` 设成 `onnx`，纯 CPU 也能跑，不必装 torch。

> 为什么张嘴分类器不用 onnxruntime：两者在真实人脸框上输出**逐位相同**

### 三个已经踩过的坑（改动前先看）

**1. torch 必须在 cv2、PyQt5 之前导入。**

torch 自带一份 OpenMP / protobuf / abseil 原生库。如果先初始化了 OpenCV 或 Qt、
之后再 `import torch`，Windows 下会**直接段错误**（退出码 139），Python 层抓不到
异常，界面瞬间消失、没有任何 traceback。原来的崩溃点固定在
`onnxruntime/capi/_pybind_state.py` 加载 DLL 那一行 —— 那张嘴分类器改用 cv2.dnn
之后这个具体触发点已经消失，但**顺序规则仍然保留**：

`run_monitor.py` 把 `_preload_vision_runtime()` 放在**所有第三方 import 之前**，
`vision/yawn_monitor.py` 的 `start()` 里也会再调一次（已加载则是空操作）。
用 `python -X faulthandler` 才能看到这个栈，普通运行只会看到"闪退"。

**2. 人脸框必须按 `_clip(x1, y1, x2, y2, width, height, score)` 传参。**

早期版本写成 `self._clip(*row[:5], width, height)`，把置信度挤进了 `width`
位，结果每个框都被裁成 0 宽后丢弃 —— 表现为"画面里明明是张大脸，检出率 0%"。
这类错误单看代码很难发现，只有跑真实帧基准（而不是纯色占位图）才暴露。

**3. 「连续张嘴 N 秒」不能一帧不达标就清零。**

真机上概率曲线会抖：人脸框轻微位移、手挡一下、模型在临界值附近跳一下，都会让
某一帧掉到阈值以下。原来一掉线就 `_open_since = None`，7fps 下「连续 1.5 秒」
需要约 10 帧全部达标，实际的哈欠几乎凑不满 —— 这是「识别不灵敏」的主因。
现在给了 `[vision] dip_grace=0.3` 的容忍窗口，窗口内不清零、界面状态也不闪。
**别调到 0.5 以上**，否则 0.5 秒级的说话张嘴会被算成哈欠（单测用例 2 守着这条线）。

### 已知限制

- **侧脸/低头会漏检**。界面会把「未检测到人脸」单独显示，不会当成"没打哈欠"。
- 阈值与 `yawn_min_sec` 都是经验参数，换场景（摄像头位置、光照）要重新标定。
- 检测结果**只显示、不入库**。要沉淀数据需另加表（当前版本未做）。
- 只取画面中面积最大的那张脸，多人同框时其他人不参与判定。

## 数据包格式（244 字节）

| 偏移 | 字段 |
| --- | --- |
| 0 | 包头 `0x5B` |
| 1 | 指令类型 |
| 2 | 包长度 |
| 3 | 未知 |
| 4:8 | 包号（uint32 大端） |
| 8 | 类型字1（`0x01` = ECG） |
| 9 | 类型1长度 |
| 10 | loff |
| 11:13 | 体温（int16 小端）/ 100.0 |
| 13:173 | 80 个 ECG 采样点（int16 小端，有符号） |
| 173 | 类型字2（`0x03` = 呼吸） |
| 174 | 类型2长度 |
| 175:191 | 8 个呼吸采样点（int16 小端，有符号） |
| 191 | 类型字3（`0x02` = 三轴） |
| 192 | 类型3长度（字节数，÷3 为采样点数） |
| 193:209 | x 轴（int8）/ 64.0 |
| 209:225 | y 轴（int8）/ 64.0 |
| 225:241 | z 轴（int8）/ 64.0 |
| 241:243 | CRC16 |
| 243 | 包尾 `0x5D` |

## 常见问题

- **扫描不到设备**：确认设备已开机并广播、蓝牙已开启；`--debug` 模式可打印服务表帮助排查。
- **连接后无数据**：用 `--debug` 查看服务/特征表，确认 handle `20/22/25` 对应关系是否与原设备一致。
- **数据乱码/丢包**：程序已内置缓冲重组逻辑，可应对 MTU 不足导致的分包。
