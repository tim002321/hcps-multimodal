# 面部 ROI 离线处理工具

把一个采集会话的原始帧批量处理成 **左右眼 ROI、嘴部 ROI、68 点标注图、指标 CSV**。
输出图片的**文件名与主程序采集时完全一致**，可直接和数据库里的 `file_name` 对上。

不动 `AAAwindows_code` 任何文件，数据库只读打开。

## 快速开始

```bash
# 先看一眼这个会话有多少帧、什么结构
.venv\Scripts\python.exe face_tool\run_cli.py --scan "D:\data\薛锦民\1_20261117_192737"

# 处理到指定目录
.venv\Scripts\python.exe face_tool\run_cli.py "D:\data\薛锦民\1_20261117_192737" -o "D:\out"

# 图形界面
.venv\Scripts\python.exe face_tool\run_gui.py
```

GUI 操作路径：选会话目录 → 点「扫描」→ 选输出目录 → 点「开始处理」。

## 输出长什么样

```
<输出根>\<会话目录名>\
├─ eyes_left\    20261117_192821_202189_000001.png     ← 左眼（PNG 无损）
├─ eyes_right\   20261117_192821_202189_000001.png     ← 右眼（PNG 无损）
├─ mouth\        20261117_192821_202189_000001.jpg     ← 嘴部
├─ landmarks.csv     一帧一行，136 个坐标列（不含任何图像）
├─ metrics.csv       一帧一行（含失败帧），带质量指标与 ROI 原图坐标
├─ run.json          参数快照 + 指纹 + 模型信息 + 环境
├─ summary.txt       人读报告
├─ errors.log        失败明细
└─ landmarks_check\  仅 --annotate 时生成：在原图上画出 68 点，用于自检
                     ⚠ 这是原图副本，含人脸，不要外传、不要归档
```

眼部用 PNG 是因为它只有约 2 KB 的信息量，JPEG 二次压缩会糊掉瞳孔边缘和睫毛细节
（实测：PNG 6.7 KB/张，JPG 2.0 KB/张，体积换保真）。文件名的主干仍与源帧完全一致，
只有扩展名从 `.jpg` 变成 `.png`；需要严格同扩展名时加 `--eye-format jpg`。

**默认不生成 `landmarks_check/`。** 68 点只以坐标形式存在 `landmarks.csv` 里。
需要肉眼核对标注质量时，临时加 `--annotate` 跑几帧，看完即删。

### 命名规则

严格照搬主程序 `devices/camera_media.py` 的规则：

```
{prefix}_{seq:06d}.jpg
prefix = YYYYmmdd_HHMMSS_ffffff      # 22 字符，开流时刻
例：20261117_192821_202189_000001.jpg # 33 字符
```

同一帧的四个产物分散在四个子目录，文件名完全相同——所以既能一眼看出对应关系，又不会互相覆盖。

注意 `prefix` 是**开流时刻**而非每帧时间；每帧真实时间在 `metrics.csv` 的 `time` 列（来自数据库
`camera_frames.time`，毫秒级）。同一会话内若重开过采集，会出现多个 prefix，序号各自从 1 开始。

## 指标口径

| 指标 | 公式 | 典型范围 |
|---|---|---|
| `ear_l` / `ear_r` | `(|p38-p42| + |p39-p41|) / (2|p37-p40|)` | 睁眼 0.25~0.40，闭眼 <0.20 |
| `ear_mean` | 两眼平均 | — |
| `mar_inner` | `|p62-p66| / |p60-p64|`（内唇） | 闭嘴 0~0.15，说话 0.2~0.5，哈欠 >0.5 |
| `mar_outer` | `|p51-p57| / |p48-p54|`（外唇） | 同上，略微平滑 |

哈欠判定建议：`mar_inner > 0.5` **且持续 > 4 秒**。只看数值会把说话误判成哈欠。
眨眼判定：`ear < 个人阈值` **且连续 ≥2 帧**（15 fps 下约 133 ms）。
个人阈值取该被试前 10 秒基线中位数的 0.7 倍，比通用阈值稳。

## 质量指标（只有这里能算）

预处理阶段还看得见原图，一旦只留 ROI 小块，这些量就永远补不回来了，所以即使当前不用也先存着：

| 列 | 含义 | 参考阈值 |
|---|---|---|
| `blur_var` | 脸部区域的拉普拉斯方差 | **随分辨率变化，必须按自己的数据标定** |
| `is_blurry` | `blur_var` 低于阈值的标记 | 默认阈值 15，按 640×480 标定，换分辨率要改 |
| `brightness` | 脸部平均灰度 | 建议 90~170 |
| `contrast` | 脸部灰度标准差 | 低于 20 说明对比度差 |
| `over_ratio` / `under_ratio` | 过曝（≥245）/ 欠曝（≤15）像素占比 | 过曝 >2%、欠曝 >15% 需留意 |
| `roll_deg` | 两眼连线倾角 | >12° 说明明显歪头 |
| `yaw_ratio` | 鼻尖水平偏移 / 眼距 | >0.18 说明明显侧脸 |
| `pitch_ratio` | 鼻尖垂直偏移 / 眼距 | 低头抬头的粗估 |

实测参考（345 帧 640×480）：`blur_var` 中位 25.3、p5 12.0、p95 36.9；亮度 102；对比度 29；
`roll` 中位 2.8°、`yaw` 中位 -0.006（基本正脸）；按阈值 15 约有 10% 的帧被判偏糊。

**这些阈值不是普适常量。** 换机位、换分辨率、换光照，`blur_var` 的分布会整体平移，
必须先在自有数据上跑一遍看分布，再定阈值——这也是把它们写成连续值而不是只给布尔标记的原因。

## ROI 原图坐标

`metrics.csv` 里每组 ROI 都带 `x1/y1/w/h`（`eye_l_*`、`eye_r_*`、`mouth_*`），
是相对于整帧的像素坐标。用途：反查某块 ROI 在原图的位置、按坐标重新裁剪、
或者把 ROI 结果叠加回原图做核对。


## 参数

CLI 参数与 GUI 一一对应，全部有默认值，一般不用改：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--backend` | `auto` | `auto/torch/onnx/dlib`，按序降级 |
| `--conf` / `--imgsz` | `0.35` / `640` | 与主程序一致，不要随意改 |
| `--face-pick` | `center` | 多脸时选中线附近的那张（与主程序同语义） |
| `--roi-mode` | `hybrid` | 脸比例与包围盒取较大者，闭眼不塌缩 |
| `--eye-w-ratio` / `--eye-h-ratio` | `0.32` / `0.19` | 眼 ROI 相对脸宽高 |
| `--mouth-w-scale` / `--mouth-h-scale` | `1.5` / `3.0` | 嘴 ROI 相对外唇包围盒 |
| `--roi-scale` | `1` | 放大倍数（最近邻，不增加信息） |
| `--jpeg-quality` | `95` | 分析端保细节；主程序采集用的 80 不变 |
| `--eye-format` | `png` | 眼部存 PNG（无损）还是 JPG；嘴部固定 JPG |
| `--annotate` | 关 | 生成 68 点自检图（原图副本，含人脸，勿外传） |
| `--overwrite` | — | 忽略已有产物全部重算 |
| `--limit N` | `0` | 只跑前 N 帧，调试用 |

**续跑**：默认跳过已存在的产物，但要求 `params_hash` 一致。改了任何影响像素的参数
（ROI 比例、质量、后端…）会自动全量重算并在日志里告警，避免两套参数混在一个目录里。

## 能力边界

1. **68 点来源**：dlib 的 iBUG 300-W 模型，人脸框用的是 YOLO 的输出。两者边距习惯不同，
   导致**下颌 0-16 号点比真实轮廓外扩 3~8 px**。眼、眉、鼻、唇不受影响，本工具的 ROI
   只用眼和嘴，所以产物不受影响。若你要用 jaw 点算脸型，需先做人脸对齐。
2. **瞳孔直径不输出**。640×480 下人眼宽约 45 px、瞳孔 6~10 px，1 px 误差就是 10% 读数误差，
   这个精度不足以做直径测量。需要瞳孔请用眼动仪（aSeeStudio）。
3. **MAR 依赖 68 点**，没有上下唇点时算不出张口高度。本工具用的是完整 68 点里的内唇点，
   所以 MAR 是可信的；但如果你换成只给 5 点的检测器，就只剩嘴角距可用了。

## 常见问题

**1) 后端掉到了 dlib，精度变差**
`auto` 会按 torch → onnx → dlib 降级。`models/` 里目前只有 `.pt`，没有 `.onnx`。
启动日志会打印三个模型的存在状态。生成 onnx：

```bash
.venv\Scripts\python.exe AAAwindows_code\tools\vision\fetch_models.py --with-onnx
```

**2) 提示「读库失败」**
主程序正在写库时会短暂锁表。本工具用只读模式 + 5 秒重试，一般能读；若持续失败，
先停掉采集再跑。

**3) 老会话没有 frames/，图在库里**
工具会自动识别（`jpeg` BLOB 结构），用库名合成前缀（如 `20261103_142134_000000`）作为文件名。
这类会话的处理会慢一些，因为要从库里解图。

**4) 中文路径**
所有读写走 `np.fromfile + imdecode`，不依赖 `cv2.imread`，中文路径安全。

## 批量模式

选一个**大文件夹**（里面装着多个会话），会自动递归找出所有会话目录，逐个处理，
输出树按原目录结构镜像：

```
输入                                   输出
D:\data\                                E:\out\
├─ 张三\                                 ├─ 张三\
│  ├─ 1_20261117_192737\                 │  ├─ 1_20261117_192737\
│  │  ├─ frames\*.jpg                    │  │  ├─ eyes_left\*.png
│  │  └─ 20261117_192816.db              │  │  ├─ eyes_right\*.png
│  └─ 2_20261118_090000\                 │  │  ├─ mouth\*.jpg
└─ 李四\                                 │  │  ├─ metrics.csv …
   └─ …                                  │  └─ …
                                         ├─ 李四\…
                                         └─ _batch_summary.csv
```

```bash
# 扫一遍看会处理哪些会话
python run_cli.py "D:\data" --scan

# 批量处理
python run_cli.py "D:\data" -o "E:\out"
```

**会话的判定方式**（命中即停，不再深入该子树）：

1. 目录里有 `frames/` 子目录 → 正常会话
2. 目录里有会话库（`camera_frames` 表）→ 老式会话，图在库里
3. 目录里直接有 ≥5 张图片 → 纯图片会话

模型的加载只做一次，各会话复用；**单个会话出错不影响其余会话**，
失败的会记进 `_batch_summary.csv` 的 `note` 列。

`--max-depth` 控制递归层数（默认 6）。如果大目录本身就是一个会话，
会自动走单会话模式，无需切换。

### 输出位置的三层防护

把输出放在输入目录里，会导致下次扫描把 `eyes_left/` 里的图当成新会话再处理一遍。
现在有三道拦截：

1. **扫描时跳过**：目录里出现 `eyes_left/`、`eyes_right/`、`landmarks_check/`，
   或含 `run.json` / `_batch_summary.csv`，就判定为"本工具的产物"，整棵子树不再深入。
2. **CLI 拒绝**：输出路径落在输入根目录（或会话目录）内部时，直接报错退出。
3. **GUI 阻止**：同样判断，弹警告并中止，不启动任务。

所以即使你误把输出设到 `data\处理后\`，也不会产生"眼睛的眼睛"。
